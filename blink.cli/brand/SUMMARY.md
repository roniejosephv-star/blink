# Tinkr Brand — Top 5 Decisions

> The five decisions that shape everything else. If you read only one document, read this one.

> **Update Aug 12, 2026 (revised same day):** Tagline revised to **"Tinker on."** (was "Tinker on." — moved on to clear the HIT/Mattel trademark question and pick a stronger two-word line).

---

## 1. **"Tinker on."** — not "Cursor for Edge Devices."

**Decision**: The headline tagline is "Tinker on." — two words, imperative, persona-broad. The shortest possible statement of the value prop.

**Why**: The original draft was "The hardware IDE that ships" (engineer-first, too jargon-y for the hobbyist persona). The morning revision was "Tinker on" (memorable, but trademark-flagged for HIT/Mattel). The afternoon revision is "Tinker on." — it beats both. Three reasons:

- **Shortest possible statement.** Two words. A tagline that needs more is a brochure line, not a tagline.
- **Imperative, not descriptive.** Tells the user what to do, not what we are. The product is the means; the user's output is the end.
- **Pairs with the wordmark.** `tinkr` + `tinker on` = the iteration loop. Tinkr is the cadence, build is the output.

**Trademark status:** No risk. "Tinker on." is entirely generic. The "Bob the Builder" concern from earlier today is fully closed.

**Personas it serves:** Mira (builds prototypes), Devansh (builds curricula), Sara (builds shipping products). All three build. The tagline doesn't segment.

**Use in product surfaces:** lowercase `tinker on` in footers, CLI banners, button labels, social bios. Sentence case `Tinker on.` in prose. Title case `BUILD IT` only in tracked marketing contexts (posters, ads). The "Cursor for Edge Devices" line stays as the investor-pitch one-liner.

## 2. **Cyan primary + amber accent.** — not blue + purple, not monochrome.

**Decision**: Primary is `#5EEAD4` (mint cyan, "circuit cyan"). Accent / CTA is `#FB923C` (orange, "LED amber"). Secondary is `#A78BFA` (violet, "code violet") for the agent / AI surface.

**Why**: Every dev tool in 2026 is either blue, purple, or monochrome. Linear is purple. Vercel is monochrome. Cursor is monochrome with a hint of blue. Raycast is red. The default for "another dev tool" is one of these three, and they are all visually crowded. The cyan + amber combination is distinctive on the dev-tool shelf without being weird for the sake of it. Three specific reasons:

- **The amber is the LED nod.** Every hardware developer has seen an amber LED on a board. The accent color is not a metaphor; it is a recognition. The "i" in the wordmark is an amber dot. When the user deploys code and the LED tinkrs, the brand and the device are the same color. The product is the bridge between the two.
- **The cyan is a working dev-tool color, not a marketing one.** Cyan works on dark surfaces, in terminals (ANSI 51), and in syntax highlighting. It carries 12.6:1 contrast on dark surfaces (AAA) and degrades cleanly in 256-color and 16-color terminals. It is the workhorse color of the palette.
- **The violet separates the human from the agent.** The agent surface, the KB entries, the AI-related elements get violet. The user-built code and CLI output get cyan and amber. The brand tells the user, visually, "this was generated by the agent" vs. "this is your code." The color is a contract.

The hard rule is that the amber is the only accent. It is the brand's signature. If a new feature needs a third accent, the answer is no — the amber is the answer.

## 3. **Dark mode by default, light mode first-class.** — not dark as a theme.

**Decision**: Dark mode is the default surface. Light mode is the alternative, with the same fidelity.

**Why**: Engineers work in dark mode. The data is clear (Stack Overflow's annual dev survey, the Linear/Warp/Raycast user base, the Cursor install base). The product is for engineers. The default is dark.

But the line "dark mode by default" is not the same as "dark mode is the theme, light mode is a stretch." Light mode has the same fidelity: same components, same contrast, same focus rings, same spacing. The two are siblings in the token file (`color.text.primary.dark` and `color.text.primary.light`), and the application picks at runtime via `data-theme` on `<html>`. The default is dark. The choice is the user's.

This decision is in the hard rules. "Light and dark mode are equal" is non-negotiable. A feature that works in dark but is broken in light is a broken feature.

## 4. **Inter + JetBrains Mono, no exceptions.** — not Geist, not proprietary fonts.

**Decision**: Inter for UI, JetBrains Mono for code. Both from Google Fonts. System fallbacks. No other fonts.

**Why**: This is the only place the brand makes a "boring" decision, and it is the right one. Three reasons:

- **Open-source constraint.** The brief says "no proprietary font dependencies." Geist (Vercel's font) is not on Google Fonts as of v0.3.0. The brand can't depend on a font that isn't on the open-source font CDN. Inter and JetBrains Mono are.
- **Dev-tool default.** Inter is what Linear, Vercel, Raycast, Warp, Cursor, and most of the dev-tool shelf use. JetBrains Mono is what VS Code, JetBrains, and most terminal configs use. When a new engineer opens Tinkr, the fonts feel familiar — not "another custom font to learn."
- **Variable fonts.** Both Inter and JetBrains Mono ship as variable fonts. One file, all weights, all axes. The bundle is small, the rendering is sharp, the design system can express every weight from 400 to 700 with one token.

The cost of being distinctive on type is paid in maintenance, accessibility, and onboarding. The benefit of being distinctive is small compared to the benefit of being instantly familiar. The brand is distinctive on color, voice, and motion. Type is the place to be boring.

## 5. **The mark is a project + an LED.** — square frame, center dot, amber "i" in the wordmark.

**Decision**: The symbol mark is a 24×24 square frame with a 6×6 filled circle centered. The wordmark "tinkr" is lowercase Inter, with the "i" replaced by a filled amber circle. The dot animates at 1 Hz (suppressed under reduced motion).

**Why**: The mark has to do three things at once:

1. **Be the Hello World of hardware.** Every maker's first project tinkrs an LED. The mark is the moment the user first sees their code do something. It is the most common artifact in the product's universe.
2. **Encode project-as-memory.** The square is the "project frame" — the user's project repo, the source of truth. The dot inside is the LED. The user's project is the container; the LED is what the project does. The mark is the architecture in one image.
3. **Work at 16 pixels.** The favicon is the most-seen brand asset. The mark has to read as a "thing" at 16×16. A square with a center dot is recognizable at 16 px. A wordmark is not.

The amber LED in the "i" is the brand's signature in the wordmark. The same dot animates at 1 Hz — the "tinkr" — in any context where motion is appropriate. The animation is the one place the brand breathes. It is suppressed under reduced motion. The mark is static in CI, in print, in non-animated contexts.

The mark is also a test. If a future brand asset doesn't compose cleanly with a square + dot, it isn't Tinkr. The mark is the design system.

## What's not in the top 5 (but is in the spec)

The full spec covers more than these five decisions. The other top-tier decisions, in order:

- **Brand archetype: Sage (primary) + Magician (secondary).** The KB is the Sage, the agent is the Magician.
- **Brand promise: "Your project is the memory. The community is the engine. Tinkr is the tool."** The test for every product decision.
- **Voice: engineer-to-engineer.** Direct, technical, dry, honest. The single test: "Would an engineer read this aloud to another engineer?"
- **Visual style: Modern Minimalism, dark by default.** Restrained, sharp, spacious, honest, dark.
- **Motion: 150 ms / 200 ms / 300 ms / 1 Hz tinkr.** Fast, purposeful, invisible. Reduced motion is respected.
- **Accessibility: WCAG 2.1 AA floor.** Color is never the only indicator. Focus rings are mandatory. Keyboard works.
- **Three personas, one product.** Mira (hobbyist), Devansh (educator), Sara (engineer). When in doubt, optimize for Sara.

These are in the relevant sections of `01-positioning.md`, `02-visual-identity.md`, and `04-component-library.md`. The top 5 are the decisions that show up first when someone asks "what is Tinkr?"

## The test for any future brand decision

When a new surface, feature, or asset comes up, ask four questions:

1. **Does it pass the engineer-aloud test?** (See `01-positioning.md` §8 for the full rule.)
2. **Does it work in both light and dark?** If not, it doesn't ship.
3. **Does it work in the terminal?** If it doesn't work in 80 columns of monospace, the GUI version doesn't ship either.
4. **Does it break one of the 8 hard rules?** If yes, the decision is wrong, not the rule.

The 5 decisions above are the answers. The 4 questions are the test. The spec is the record.
